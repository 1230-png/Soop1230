## 1. 두 문서는 무엇인가

| 축 | 문서 A · 완성 가이드 | 문서 B · 현재 파일 정리 |
|---|---|---|
| 성격 | 설계 + 설치 매뉴얼 + 전체 소스코드 | 실측 감사 보고 + 불일치 지적 |
| 시점 | 구현 직후 (선언) | 운영 후 (검증) |
| 주장 | "완성 및 테스트 완료 · 프로덕션 준비" | "신뢰하지 마시고 확인이 필요합니다" |
| 근거 | 없음 — 실행 결과 미제시 | Drive 실물 조회 (파일 수·노트 내용·타임스탬프) |
| 가치 | 재사용 가능한 코드 골격 | 무엇이 왜 실패했는지에 대한 증거 |
| 치명적 한계 | 검증 없이 완성 선언 | 진단만 있고 수정 코드가 없음 |

두 문서는 모순이 아니라 **짝**이다. A에서 코드 골격을, B에서 파손 지점 목록을 가져오면
새 파일은 `A의 구조 + B의 수정 목록`으로 조립된다.

## 2. 설계된 경로 vs 실제로 벌어진 일

문서 A의 5단계 파이프라인에 문서 B의 관측 결과를 겹쳐 본 것.

| 단계 | 문서 A의 설계 | 실제 결과 |
|---|---|---|
| ① 폴더 스캔 | 감성힙합 / EDM 순회 | **정상** — 유일하게 문제없는 단계 |
| ② SHA256 대조 | 처리 이력 필터 | 파일명만 바꾸면 영영 스킵. 매 실행 3.5GB 재해싱 |
| ③ 가사 추출 | mutagen 태그 읽기 | **항상 빈 문자열** — Suno 파일에 가사 태그 없음 |
| ④ 중복 판정 | 제목 + 가사 유사도 (90/80/75%) | **입력이 없어 무력화** — 유사도 전부 0.0 |
| ⑤ 노트 생성 | Vault 에 `.md` 쓰기 | 전 곡 동일 플레이스홀더, 생성일까지 141곡 동일 |

**③의 실패가 ④를 죽인다.** 그리고 두 문서 어디에도 **오디오를 보관함으로 복사하는 경로가 없다** —
PC에서 지우면 Obsidian에서도 사라진다.

## 3. 항목별 세분화

### 3-1. 경로와 저장 구조

| 항목 | 문서 A (설계) | 문서 B (실측) | 차이의 의미 |
|---|---|---|---|
| 보관함 이름 | `음시디언_음원노트` | `옵시디언_음원노트` + 오타 폴더 별도 존재 | **치명** — 오타 한 글자로 보관함이 두 벌로 갈라짐 |
| 기준 경로 | `C:\Users\admin\내 드라이브` (로컬 PC) | Drive 클라우드에서만 결과 확인 가능 | 클라우드 세션은 PC를 못 봄 — 실행 위치 결정 필요 |
| 소스 ↔ 보관함 | 분리 | 분리되어 있었으나 보관함 삭제됨 | **신규** — 오디오 사본이 보관함 안에 있어야 함 |
| 오디오 취급 | 읽기만 — 복사·이동 없음 | 원본 폴더에 그대로 (141곡) | **R1 미충족** |
| 현재 폴더 | 3단 구조 전제 | 보관함·로그·스크립트 폴더 전부 소실 | 평면 구조에서 재시작 — 설계 자유도 확보 |

### 3-2. 노트 템플릿 필드

| 필드 | A가 정의한 값 | B가 관측한 값 | 새 시스템 |
|---|---|---|---|
| 카테고리 링크 | `[[감성힙합]]` / `[[EDM]]` | 그래프 연결 동작 | 그대로 채택 |
| 파일명·형식·크기 | 자동 | 정상 기록 | 그대로 채택 |
| 생성 날짜 | `getctime` | 141곡 전부 `2026-08-23 05:51:06` | **교체** — Suno 생성일 또는 mtime |
| 가사 | 태그에서 자동 추출 | 전 곡 비어 있음 | **전면 재설계** — 3단 폴백 |
| Suno Style | `[사용자 입력]` | 전 곡 `EDM, melodic, atmospheric` 동일 | **전면 재설계** — 배치 문서 회수 |
| BPM | `[사용자 입력]` | 비어 있음 | **신규** — 배치 문서 또는 실측 |
| 무드 / 장르 | `[사용자 입력]` | 전 곡 `신나는` / `EDM` 동일 | **교체** — Mood·Palette 코드 체계 |
| Exclude 프롬프트 | 없음 | 없음 | **신규** — 배치 문서에 존재 |
| 오디오 임베드 | 없음 | 없음 | **신규** — `![[파일.wav]]` |
| youtube_url | 없음 | 없음 (B가 명시적으로 지적) | **신규** — 업로드 추적 |
| YAML 프론트매터 | 없음 (전부 본문 텍스트) | 없음 | **신규** — 쿼리·정렬에 필수 |

> 마지막 줄이 핵심이다. 문서 A는 모든 정보를 본문 마크다운으로 썼기 때문에
> "BPM 90 이상인 곡" 같은 조회가 불가능하다. YAML 프론트매터로 옮기면 Dataview 한 줄로 전곡 표가 나온다.

### 3-3. 중복 감지

| 계층 | A의 설계 | 실제 결과 | 판정 |
|---|---|---|---|
| 파일 해시 | SHA256 전체 읽기 | 동작하나 141곡 × 평균 25MB 매 실행 재해싱 | 유지·개선 (크기+mtime 1차 필터) |
| 제목 일치 | 확장자 제거 후 소문자 비교 | 번호 접두사(`78.`) 때문에 사실상 항상 불일치 | **수정** — 접두사·괄호 정규화 |
| 가사 유사도 | 90% 중복 / 80% 의심 / 75% 경고 | 가사가 없어 전부 0.0 — 한 번도 발동 안 함 | 가사 확보 후 부활 |
| 순회 로직 | 모든 노트 검사 | 75%를 넘는 **첫** 노트에서 즉시 반환 — 뒤쪽 미검사 | **버그** — 최고 유사도 채택으로 변경 |
| 주제·훅 중복 | 없음 | 없음 | **신규** — 채널 운영상 진짜 필요한 건 이것 |

### 3-4. 가사·프롬프트 확보 경로

| 경로 | A | B | 실현 가능성 | 커버 |
|---|---|---|---|---|
| 오디오 태그 | 유일 수단으로 채택 | 결과 0건 | **불가** — Suno 파일에 가사 태그 없음 | 0 / 141 |
| 배치 문서 대조 | 없음 | 없음 | **검증됨** — 제목 4건 + 훅 1건 | 5 / 141 |
| 과거 기록 수집 | 없음 | 없음 | 수동 1회 — 곡 로그를 채워두면 이후 자동 | 가변 |
| 전사 + AI 복원 | 없음 | 없음 | **신규** — Whisper 전사 → Claude/Gemini 정형화 + Style 역추정 | 136 / 141 |

EDM 63곡은 제목이 전부 영어(`1.Echoes of the Crimson Moon`, `4.Seoul Blue` …)이고
대응 배치 문서가 없다. 그래서 4번째 경로는 선택이 아니라 **필수**다.
정확도가 필요한 감성힙합은 2번 경로, 물량이 필요한 EDM은 4번 경로로 나누는 것이 현실적.

## 4. 새 요구 4건 × 기존 문서 충족도

## 5. 새 파이프라인 제안

```
드롭 폴더 ──복사(이동 아님)──▶ 보관함/_audio/  ◀── 보관함이 원본을 소유
   │                                  │
   │                                  ▼
   ✕ PC에서 원본 삭제          보관함/곡제목.md
     → 보관함 사본은 무사        YAML + 가사 + Style + Exclude
                                 ![[_audio/곡제목.wav]]
                                        ▲
                                        │ 채워 넣기
                        ┌───────────────┴────────────────┐
                        │  메타데이터 3단 폴백            │
                        │  1단 배치 문서 제목·훅 매칭     │ 정확도 최상 · 현재 5곡
                        │   └실패▶ 2단 오디오 파일 태그   │ 제목·아티스트 정도
                        │      └실패▶ 3단 전사 + AI 복원  │ Whisper → Claude|Gemini
                        └────────────────────────────────┘
                        프로바이더 1줄 전환 — claude ⇄ gemini
```

처리 이력·중복 판정·실패 사유는 곡 로그 CSV 한 곳에 누적해,
다음 배치 설계와 중복 검사가 같은 원천을 보게 한다.

## 6. 재조립 모듈 메뉴

각 줄은 독립적으로 넣고 뺄 수 있다. 필요한 번호만 지정하면 그 조합으로 새 파일을 조립한다.

| 번호 | 모듈 | 하는 일 | 출처 | 빼면 생기는 일 |
|---|---|---|---|---|
| **M1** | 오디오 보관함 복사 | 드롭 폴더의 곡을 보관함 `_audio/`로 복사하고 노트에 임베드 | 신규 | PC에서 지우면 Obsidian에서도 사라짐 (R1 불가) |
| **M2** | 배치 문서 색인 | `3AM_08.23` 같은 문서를 파싱해 곡별 Style·가사·BPM 색인 구축 | 신규 | 자동 채움의 가장 정확한 경로가 사라짐 |
| **M3** | 제목 정규화 매칭 | `78.제목 (English)`에서 번호·괄호를 벗겨 대조, 훅 가사 역매칭 포함 | 신규 | M2가 있어도 파일명이 달라 못 찾음 |
| **M4** | 전사 + AI 복원 | Whisper로 가사 전사 후 AI가 정형화하고 Suno Style 역추정 | 신규 | 배치 문서 없는 136곡은 영영 빈칸 |
| **M5** | Claude · Gemini 전환 | 프로바이더 추상화 — 설정 한 줄로 교체, 프롬프트 규격 공유 | 신규 | 한쪽 AI에 고정 (R3 불가) |
| **M6** | YAML 프론트매터 | BPM·무드·상태·youtube_url을 조회 가능한 속성으로 기록 | 신규 | Dataview 조회·정렬 불가 |

## 7. 선행 결정

### ✅ 결정됨 (2026-08-22)

**1. 보관함 위치 — Drive 밖 로컬 경로**

예: `D:\ObsidianVault`. 드롭 폴더(`내 드라이브\감성힙합`, `내 드라이브\EDM`)에서
오디오를 **복사**해 보관함에 넣는다. 보관함이 Drive 동기화 대상 밖에 있으므로,
PC에서든 Drive에서든 원본을 지워도 보관함 사본은 영향을 받지 않는다 — **R1 충족**.

- 트레이드오프: 보관함 자체의 클라우드 백업은 없다. 별도 백업 수단을 나중에 붙일 수 있다.
- 구현상 함의: 경로는 `config.json`으로 빼서(M15) 보관함을 옮겨도 코드를 안 고치게 한다.

**2. 가사·프롬프트 복원 범위 — 앞으로 넣는 곡만**

기존 141곡은 **오디오 복사 + 노트 생성까지만** 수행하고, 전사 + AI 가사 복원(M4)은
새로 들어오는 곡부터 적용한다.

- 기존 141곡에 대해서도 M1(오디오 복사) · M6(프론트매터) · M7(카테고리 링크)은 전곡 적용된다.
  즉 141곡 전부 "옵시디언에서 재생되는 노트"는 즉시 확보된다. 가사 칸만 비어 있을 뿐이다.
- 배치 문서로 회수되는 5곡은 예외적으로 지금 바로 채워진다 (M2·M3은 비용이 들지 않으므로).
- 나중에 마음이 바뀌면 M4를 소급 모드로 한 번 돌리면 된다 — 노트를 다시 만들 필요는 없다.

### ⏳ 미결

**3. 3AM과 EDM은 같은 시스템인가.** 문서 B가 지적한 "Rush22 / 3AM" 명칭 불일치가 미해소.
현재 Drive 폴더는 `감성힙합`·`EDM`, 저장소 `channel/`은 "새벽공기"라는 또 다른 채널이다.
이름 체계를 통일할지, 채널별로 보관함을 나눌지 결정 필요.
